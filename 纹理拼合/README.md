# 纹理拼合 · 生成正方形图 → 切 9 块 → 按纹理拼回

纯前端单文件，双击 `index.html` 或访问 http://127.0.0.1:8002/ 即可。

## 它做什么

1. **生成**一张 600×600 的正方形图（渐变底 + 46 个随机色块 + 60 条随机斜线，故意让形状跨越切缝）；
2. **切分**成 3×3 = 9 块，每块 200×200；
3. **打乱**成随机排列（保证不是原序）；
4. **纹理检测拼合**：**不看位置、不知道原图排布**，只比较相邻两块边缘像素的连续性，搜出接缝代价最小的排列。

## 纹理检测怎么算

对每一块取它四条边的像素（`L / R / T / B`），两两计算接缝代价：

```
横缝(a 在左, b 在右) = mean( (a.R - b.L)² )     ← 逐行逐通道
竖缝(a 在上, b 在下) = mean( (a.B - b.T)² )
```

同一张图切开的相邻两块，边缘列本来就是相邻像素，代价极小；不相关的两块是随机颜色，代价大一个数量级。

然后**分支限界**搜索：按行优先逐格填，每填一格就把「左边缝 + 上边缝」的代价累加，一旦超过当前最优就剪枝。等价于遍历所有 9! = 362880 种排列，但因为正确解的代价接近 0，剪枝极狠，实际 **< 1 ms**。

## 页面显示

- 左：打乱后的 9 块（`#编号` 可切换显示，用来核对）；
- 右：拼合结果，并画出 12 条接缝（**越绿 = 代价越小 = 越像同一张图切开的**）；
- 下方：总接缝代价、平均每条缝、与「任意两块硬拼的代价中位数」的倍数（倍数越大越确信）。

因为图是自己生成的，正确答案一定是 `0..8`，所以能直接判定对不对。

## 不规则切割 + 用「拼图还原项目」的原理拼回

九宫格太规整了。`tools/irregular_cut.py` 把一张方图按 **Voronoi 分割**切成 N 块**不规则多边形**（每块形状、边数、面积都不同，完全不是矩形），然后复用 `拼图还原项目` 里的拼装内核去拼：

- 数据格式：直接产出项目认的 `pieces.json`（`id / polygon / area / centroid / edges`）；
- 拼装原语：`assemble.Piece`、`assemble.place_edge`、`assemble.world`、`geometry.poly_overlap_area`；
- 规则：**只允许平移 + 旋转**（不镜像、不缩放），shapely 精确拒重叠，边长要贴合。

```bash
# 单张
python 纹理拼合/tools/irregular_cut.py --image 纹理拼合/照片/001.jpg --n 6 --out 纹理拼合/示例_不规则
# 批量
python 纹理拼合/tools/irregular_cut.py --bench --limit 12 --n 6
```

产物：`cut.png`（切割示意）、`assembled.png`（拼合结果）、`pieces.json`、`report.json`。

### 但项目原来的 `beam_search.py` 直接用在上面是失败的

先照原样调用 `beam_search.py`，结果**拼错**：

```
完整拼法 200 个，最好 缝 6.16%      ← 看着挺像
真实排列 vs 搜到的排列：质心误差 0.79
真解在 beam 里吗：不在（最小质心误差 0.55）
```

原因不是匹配太松（把 `--cov` 提到 0.95 也是同样结果），而是 **`beam_search` 用「凸包空隙」给部分拼装打分**：

> 不规则碎片零散摆两三块时，凸包天然远大于已摆面积，空隙一定很大 → 真解在中途就被剪掉了。

### 改法：换状态排序准则

保持 `beam_search` 的展开逻辑不变（同样的 `place_edge` / `world` / 重叠拒绝），只把「状态优劣」从**凸包空隙**换成**对接边长不一致度**：

```
这一对的代价 = |La − Lb| / max(La, Lb)  +  0.5 × (1 − 贴合比例)
state 代价   = 每接上一块累加
```

正确的对接边长几乎相等、贴合比例 1.0，代价接近 0，于是真解一路排在前面。

### 结果

| 场景 | 成功率 | 质心误差 | 凸包空隙 |
| --- | --- | --- | --- |
| 6 块不规则，12 张真实照片 | **12/12** | 全部 **0.0000** | 全部 **0.0%** |
| 9 块不规则，单张 | ✓ | 0.0000 | 0.0% |

6 块约 5~8 秒/张，9 块约 30 秒。示例见 `示例_不规则/cut.png`（怎么切的）和 `assembled.png`（拼回来的）。

## 真实手撕纸条（`手撕拼图.jpg`）—— 形状 + 纹理实战

`tools/handmade_puzzle.py`：真实照片，4 张白色纸条散落在黑底上，纸条上有蓝色笔迹。

```bash
python 纹理拼合/tools/handmade_puzzle.py --image 手撕拼图.jpg --out 纹理拼合/手撕拼图 \
       --tex-k 4 --cov 0.35 --overlap 0.02
```

产物：`3_对比效果图.jpg`（左原图 / 右拼合结果，**两边都带 `#1`~`#4` 碎片编号**）、`2_拼合结果_*.jpg`、`solution_*.json`、`report.json`。

**分割很简单**：黑底 + 白纸，灰度阈值 100 就得到干净的 4 块（笔迹是深蓝、低于阈值，用外轮廓重填补洞）。

### 结果

| 方案 | 空隙 | 矩形贴合 | 内部接触边 | 接缝 | 笔迹不连续 |
| --- | --- | --- | --- | --- | --- |
| 纯形状 | 0.79% | 92.4% | **1400 px** | **3 条** | **0.8%** |
| 形状+纹理 | 0.79% | 92.4% | 1400 px | 3 条 | 0.8% |

最终摆法：`#1—#3—#4—#2`，三条全是干净的共线接触：

```
#1-3  共线 485 px      #3-4  共线 465 px      #4-2  共线 450 px
旋转：#1 0°   #3 355.7°   #4 176.5°   #2 336.1°
```

### ★ 关键修改：排序准则从「局部代价」换成「内部接触边总长」

这一版之前是**错的**，靠用户指出来才发现。问题在于：`#1+#3` 和 `#2+#4` 各自都能拼得很好（局部边长代价极低），但要把**两个整体再接起来**，需要整体相对旋转 —— 局部的边长代价给不出这个偏好，搜索会停在「差一条边」的解上。

实测同一张图、同一个搜索，只换完整解之间的排序准则：

| 排序准则 | 内部接触边 | 接缝数 | 空隙 | #2 旋转 |
| --- | --- | --- | --- | --- |
| `seam`（局部代价最小） | 950 px | 2 条 | 2.89% | 155° ✗ |
| `rect`（贴合最小外接矩形） | 36 px | 1 条 | 1.69% | 344° ✗ |
| **`joined`（接触边总长最大）** | **1400 px** | **3 条** | **0.79%** | **336° ✓** |

两个被否决的准则各有各的坑：

- `seam` 只顾局部，会停在「两块拼得极好、另两块没接上」的解；
- `rect` 会被钻空子 —— 四块**并排摆着但不真的贴**，并集的最小外接矩形照样很大，贴合率能到 96%。所以 `rect` 必须先要求覆盖率（最大连通块占全部面积）≈1，而「接触边总长」天然同时管住了这两件事。

现在 `assemble(rank=...)` 默认 `joined`。换成 `joined` 后，之前 12/12 的 Voronoi 基准**无回归**（仍是全部精确复原）。

### 纹理在这张图上踩的两个坑

1. **采样距离不能太小**。纸片是手撕的，边缘有一圈暗边带（跨缝灰度剖面：−4px 处 20，+4px 处 243）。`k=0.35` 时采样点正好落在暗边带上，把「笔迹连续性 1.2%」的好接缝判成 0.81 的高代价；`k=4` 落在纸面上才正常。所以 `--tex-k` 必须可调：
   - 从**连续照片切出来**的碎片（Voronoi 那种）→ 用 **0.35**
   - **分开拍、分开撕**的实物碎片（边缘有暗边带）→ 用 **3~5**
2. **白纸区域没有纹理信息**。纸条大面积是纯白，接缝两侧都是白 → 跨缝差和块内差都 ≈0，纹理项无从判断。真正带信息的只有笔迹穿过接缝的几个采样点。所以纹理在「白纸拼图」上天生偏弱。

### 那 8 张为什么错 —— 我先猜错了

我一开始以为是"边缘太平坦，纹理不够"。**数据否掉了这个猜测**：

```
成功样本的边缘标准差： min 12.31   中位 38.93   max 72.18
失败样本的边缘标准差： min 16.62   中位 33.77   max 56.76
```

两者几乎没差别，`057.jpg` 边缘标准差 56.76（算很高）照样错。于是继续查：把「真实排列的接缝代价」和「搜到的排列代价」直接对比 ——

```
照片        搜到的代价     真实排列代价        差值   结论
007.jpg      1778.2        2238.1        -459.9   启发式选错（另一拼法更顺）
080.jpg     10094.9       18045.6       -7950.7   启发式选错（另一拼法更顺）
057.jpg      3536.5        4589.8       -1053.3   启发式选错（另一拼法更顺）
（8 张全部同类）
```

**搜到的排列代价比真实排列还低** —— 说明分支限界没有 bug（它确实找到了全局最优），是**代价函数本身选错了**：只看紧邻 1 列像素太近视，大片纯色（天空、墙面、水面）里，错误的拼法在接缝处也很连续。

### 改法：用局部变化归一化

```
raw   = mean((a.外列 − b.外列)²)                    ← 接缝处的差异
base  = 0.5·(a 内侧相邻列差² + b 内侧相邻列差²) + 1  ← 这附近"本来就有多少变化"
代价  = raw / base
```

天空这种本来就很平的地方 `base` 小、比值大，于是不再被当成好接缝；而真正的接缝处，`raw` 小、`base` 大，比值接近甚至小于 1。

判别倍数（随机硬拼代价中位数 ÷ 正确拼接平均缝代价）在 100 张上的分布：

```
p0 4.33× · p25 15.07× · p50 28.70× · p75 54.09× · p90 167.47× · p100 1412.42×
```

即最差的一张也有 4.3 倍余量。

## 怎么保证「没抄答案」

这是个很自然的质疑：既然图是我们自己生成的，正确排列就是 `0,1,2,…,8`，那求解器只要原样输出下标顺序就"对了"。

所以页面在求解前多做了一步 —— **随机重新编号**：

```js
var raw  = sliceTiles(source);          // raw[i] = 原图第 i 格的像素
var perm = randPerm(9);                 // perm[t] = 编号 t 这块来自原图第几格
state.tiles = perm.map(p => raw[p]);    // 交给求解器的只有像素
var res = solveByTexture(state.tiles);  // ← 求解器拿不到 perm
```

`perm` **从不传入求解器**，求解器只收到 9 组边缘像素（L/R/T/B）。它输出的 `res.order` 是"编号空间"里的排列，跟原图格号没有直接关系。最后才用 `perm` 把结果映射回原图格号打分：

```js
right = res.order.every((tileId, k) => perm[tileId] === k);
```

### 还没验证的部分（诚实说明）

- **渲染没在真浏览器里跑过**。canvas 绘制、CSS、按钮交互只做了静态检查（括号配对 + 关键函数存在性）。`verify_kernel.py` 验证的是算法内核，不是 DOM 层。
- 算法在 **3×3、不旋转、纹理足够丰富** 的前提下有效。换成大面积纯色、或允许旋转，会失败。

## 已知限制

- 只处理 3×3 且**不允许旋转/翻转**（只做平移）。如果允许旋转，每个格子多 4 种朝向，搜索空间 ×4^9，需要换更好的剪枝或回溯策略。
- 如果图本身有大面积纯色（比如一半是天空），那条缝的代价对谁都差不多，靠边信息就分不出来 —— 这也是为什么生成图里故意撒了大量随机色块和斜线。
