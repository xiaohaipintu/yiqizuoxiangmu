# 网页版（局域网 · 手机扫码即用）

拍一张碎片散落的照片 → 上传 → 服务器跑完整条流水线 → 返回拼好的图。

## 启动

双击 `start.bat`，或在 `拼图还原项目/` 目录下执行：

```bash
python web/server.py --port 8000
```

启动后终端会打印：

```
本机访问 : http://127.0.0.1:8000/
手机访问 : http://192.168.102.62:8000/     ← 手机连同一个 Wi-Fi，扫码或手输
```

终端里还会直接打出二维码（`█▀▀` 那种方块图），手机相机扫一扫就能打开。

## 页面怎么用

1. 点「选择照片 / 拍照」，选一张碎片照片（手机可直接拍）
2. 有弯边、缺角的凹形碎片，把「有凹形碎片」保持为「是」
3. 等进度条走完 → 左边是你拍的原图，右边是拼好的图，可长按/点按钮保存

**跑的过程中就能看到图**，不用干等进度条：进度卡片下方有「实时预览」，流水线每完成一步就自动冒出一张：

| 时机 | 出现的图 |
| --- | --- |
| 分割完（~2s） | 碎片编号图 `02_pieces.png`、抠图结果 `03_cutouts.png`、前景掩膜 `01_mask.png` |
| 束搜索中 | `beam_progress.png`，**每搜完一层就刷新一次**，能看着拼装一层层长出来 |
| 评估完 | 候选排名 `41_union_rank.png` |
| 渲染完 | 成品 `assembled.jpg` |

预览区上方的阶段标签可以点，手动选一个阶段后就固定看它（不再自动跟到最新）。

**中途想换照片**：进度卡片底部有个「暂停 · 换一张照片」按钮。点一下立刻退出等待、回到上传页，可以重选/重拍一张直接重跑。后端会在**下一个步骤边界**丢弃剩余工作（正在跑的那个子步骤会跑完，比如 beam 搜索最多再等它几十秒；还没轮到 eval / render / 打包就会被跳过），结果不再产出。

**搜索时长不用你选** —— 服务器按碎片数量和形状自动定预算，拼得不够吻合会自己加时重搜（见下节）。

底部「查看候选排名图」里还有最佳四名的对比图和分割掩膜，方便判断哪一步出了问题。

## 搜索时长是怎么自动定的

`pipeline.beam_plan()` 先按碎片数给一个基础预算，再按平均边数加权（凹形/多顶点碎片搜索空间大）：

| 碎片数 | 2 | 3 | 4 | 5 | 6 | 7+ |
| --- | --- | --- | --- | --- | --- | --- |
| 基础预算 | 5s | 8s | 18s | 35s | 50s | 70s |

平均边数 > 8 时基础预算 ×1.4。然后**按结果好不好决定要不要加时**：

```
第 1 次：基础预算       → 检查候选
第 2 次：2 倍预算       → 检查
第 3 次：3.5 倍预算     → 检查
```

「够好」的判据（`pipeline.beam_ok()`）：

1. 至少 n−1 对边整条贴住（share ≥ 90%）—— 碎片得串成一串
2. 对接边的长度差平均 ≤ 4%

只要满足就立刻停，不再浪费时间；solve() 里还有 150 秒总时长硬上限兜底。实测：

| 样例 | 预算 | 实际搜索 | 判定 | 总耗时 |
| --- | --- | --- | --- | --- |
| 3 块 | 8s | 2.4s（一次就够好） | `A2↔B6` 差 2.75% | 8.6s |
| 4 块 | 18s | 16s（一次就够好） | 三条边差 3.84% | 27.2s |

页面的「拼合关系」卡片会显示「选中的候选 beam#2 · 对接边长度差 2.75% · 搜索预算 8s（自动加时，共搜了 N 次）」。

## 碎片与边的命名（方便两人沟通）

页面上的图默认带名称，右下「图上显示名称」可切换显示 / 隐藏。

| 对象 | 名字 | 规则 |
| --- | --- | --- |
| 碎片 | `A`、`B`、`C`… | 按 `pieces.json` 里的顺序（26 块之后 AA、AB…） |
| 边 | `A1`、`A2`… | 从**最上面的顶点**开始（同高取最左），按顶点顺序环状编号；第 k 条边 = 第 k 个顶点 → 第 k+1 个顶点 |

**原图和拼好的图上标的是同一套名字**，因为拼合过程只对碎片做刚体变换，顶点顺序不变。所以可以直接说「B 的 B2 边接 C 的 C1 边」。

> ⚠️ 这里有个必须注意的实现细节（曾经出过的 bug）：边编号起点是「最上方的顶点」，而碎片在成品图上被**旋转**过，它的「最上方顶点」会变。如果在成品图上重新算一遍起点，同一块碎片的边名就会整体错位（实测 B 错位 3 位：原图 B1 在成品图上被标成 B2）。所以起点必须**在原图上算一次，成品图直接复用**——`pipeline.edge_start_index()` 算出的索引会贯穿 `solves()` 全程。

页面下方的「碎片 / 边的名称对照表」会列出每块碎片的顶点数、面积，以及每条边的名字和像素长度——边长相近的两条边才可能是对接边，对照表就是用来干这个的。

再往下「**拼合关系**」直接给出结果里哪条边接了哪条边（按共线采样点的贴合比例算，≥30% 才算贴上），例如：

```
A1 ↔ C4  贴合 100%      A10 ↔ B1  贴合 100%      C1 ↔ D4  贴合 100%
另有 17 条边属于外轮廓
```



## 拍照要求（成功率的关键）

- 碎片放在**纯色背景**上（绿/白最佳），不要用花纹桌布
- 碎片之间**不要互相压住**，留一点缝
- 光线均匀、不反光，整张照片别太暗
- 碎片占画面尽量大，边缘留白即可

不满足这些条件时，第一步分割就会少块或多块，后面怎么搜索都拼不对。

## 参数（可调）

页面上的参数会作为请求头传给后端：

| 页面控件 | 请求头 | 说明 |
| --- | --- | --- |
| 有凹形碎片 | `X-Concave: 1/0` | 是否给 `segment.py` 加 `--concave` |

搜索时长**不再由用户指定**：`/api/solve` 不接受 `X-Beam-Time`（旧版客户端传了也会被忽略），一律走自动预算 + 自动加时。

## HTTP 接口（前端就是调这四个）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/solve` | body = 图片原始字节（不是 multipart），返回 `{"id": "..."}` |
| `POST` | `/api/cancel?id=...` | 暂停：只打标记不杀进程，worker 在步骤边界丢弃剩余工作；返回 `{"cancelled": true}` |
| `GET` | `/api/job?id=...` | 任务状态：`status`(queued/running/done/error/cancelled)、`step`、`progress`、`log`、`result`、`cancelled` |

| `GET` | `/api/file?id=...&n=文件名` | 取结果文件，白名单见 `server.py` 的 `ALLOWED_FILES` |

## 实现要点（踩过的坑）

1. **成品图不是 `41_union_rank.png`** —— 那张是四个候选并排的排名图。真正的拼好图由 `pipeline.render_assembled()` 现场渲染：读 `best_union.json` 的 `polys` 和 `pieces_scaled.json` 的多边形，用顶点对拟合相似变换，把每个碎片的**真实像素** warp 回位。
2. **不要用 `placed` 里的 `rot/tx/ty` 自己算仿射** —— 旋转符号约定和顶点顺序对不上会贴出一张全白图。改用 `cv2.estimateAffinePartial2D(源多边形, 世界多边形)`，并用顶点残差（<2% 碎片尺度）做质量校验。
3. **Windows 下 cv2 读不了中文路径** —— 所有任务目录都放在系统临时目录（纯 ASCII）：`%TEMP%\jigsaw-jobs\<job_id>\`。本仓库路径含中文，所以 `input/` 也不能直接喂给 `cv2.imread`。
4. **子进程必须强制 UTF-8** —— `src/*.py` 会打印 `px²`，Windows 控制台默认 GBK，管道模式下直接 `UnicodeEncodeError` 崩掉。`pipeline.child_env()` 里设置了 `PYTHONIOENCODING=utf-8`。
5. **流水线串行执行** —— `beam_search.py` 是 CPU 密集型，并发跑会互相拖慢；`server.py` 用队列 + 单 worker。

6. **`eval_union.py` 的排序不够用，必须自己重排候选** —— 它只看空洞率和重叠率，可是**接错边的拼法同样是 0 空洞 0 重叠**（错边相接一样能拼满）。实测 3 块那份：正确解是 `A2↔B6`（对接边长差 2.7%），但 `eval_union` 把 `A2↔B5`（差 4.0%）排到了第一，于是拼出来就是错的。
   `pipeline.rerank_solutions()` 因此重新排序：要求每块碎片至少接上一条边（share ≥90%），再按**对接边长度差的平均值**从小到大挑，结果写进 `chosen_solution.json`，UI 上会显示「选中的候选 beam#2 · 对接边长度差 2.74%」。

7. **贴碎片不能只按多边形裁剪** —— 分割出的多边形边界比纸片本身大 1~2px（抗锯齿/毛边），直接按多边形填会把碎片周围一圈**背景色**也贴进去，拼好后每条缝和整个外轮廓都镶一条绿边，看起来就像"没拼上"。现在用 `01_mask.png` 前景掩膜再抠一次（`warpAffine` + 外扩 1px），实测背景色像素从 5656 降到 75，细长绿条 2 条 → 0 条。

8. **"外扩 1px" 其实是错的** —— 它是对**二值**掩膜做 `dilate(3×3)`，会把碎片外侧的背景像素重新拉回来，等于每块又镶一条绿边；而且二值掩膜是硬边，抗锯齿的半背景像素被整块贴进去。现在改成：
   - `segment.py` 额外输出 `01_alpha.png`（按 Lab ΔE 做的 0~255 渐变软边蒙版，掩膜外 1px 内才允许渐变）；
   - `render_assembled()` 用 alpha 做**软合成** `dst = src·α + canvas·(1−α)`，删掉 `dilate`；
   - 软边后拼缝会留发丝白线，于是把「不接触画布边缘、且 ≤400 px 的小白块」当缝隙做 `cv2.inpaint` 填平（`info["seam_filled_px"]` 记录填了多少）。

   实测成品图里接近背景色（ΔE<40）的像素 = **0**；残余内部封闭白块 82 px（占画面 0.012%，且多为拼法本身没拼满的真实空洞）。

9. **掩膜里的孤立杂点也是"没抠干净"** —— `ΔE>40` 会在背景上留下小污点连通块（本样例 1 个、801 px）。它们面积小于 `--min-area` 所以不会成为碎片，但会画进 `01_mask.png`。`segment.py` 现在用 `drop_specks()` 直接抹掉，并保留原始掩膜为 `01_mask_raw.png` 备查；同时输出 `03_cutouts.png`（逐块白底抠图预览），抠得干不干净一眼就能看。

10. **绿幕背景应该用「色度抠像」而不是全量 ΔE** —— `segment.py --mode auto` 现在会先判断背景是不是绿幕（HSV 色相 40~85、饱和度 ≥90），是就自动切到色度抠像：
    - 距离只算 **Lab 的 a/b 通道**，完全不看亮度 L。阴影、光照不均只改 L 不改 a/b，所以影子不会被误判成前景（影子把直边切成两段 → 假角 → 接错边，就是这条链）。
    - `--chroma-lo/-hi`（默认 10 / 22）控制色度软边过渡区间，直接产出 `01_alpha.png`。
    - 再做 **despill**：绿幕反光会把绿打到纸片边缘，把 G 压到不超过 max(R,B)，其余通道不动。只在前景范围内改色，背景保持原样。结果写成 `01_despill.jpg`，`render_assembled()` 优先用它当贴图源。
    - 实测（pieces5）：前景内绿色溢出 >10 的像素 **137994 → 2162**，>40 的 **101415 → 0**；成品图绿色溢出 0 px、接近背景色 0 px。
    - 非绿幕背景（白纸、桌面等）仍走原来的 Lab 全量 ΔE，行为不变。

    更进一步：**绿幕 + 画面里只有一种颜色的纸片**时，`auto` 还会自动收窄成「只保留这个色相带」。`dominant_foreground_hue()` 统计非背景像素的色相直方图，找覆盖率最高的 30-bin 窗口；覆盖率 ≥85% 就启用。色度抠像会把反光、阴影、桌面、白纸边全留下，色相带能把这些一并切掉。

    实测两例：`三角形测试图`（粉纸片）主体色相带 H 155~5 覆盖前景 **96.9%**，抠出 4 块（1 块 11 顶点凹形 + 3 个小三角），多边形内夹带背景 0.02%~0.56%；`pieces5` 色相带 H 157~7 覆盖 **98.3%**。也可以手动强制：`--mode pink`（H 145~175）或 `--mode chroma`。

8. **影子会把一条直边切成两段** —— 纸片旁边的投影被算进前景，多边形就多出一个"假顶点"。实测那张 3 块的照片，C 的左上边被影子切成 C1(426px) + C2(394px) 两段，假顶点内角 **170°**（真角分别是 49°/88°/52°）。
   后果不只是名字多一条：`beam_search` 拿 426/394 两段短边去和别人的 830px 长边配对，拼出一个空隙 10.9% 的**错解**。
   `pipeline.clean_pieces()` 因此在分割后加了一步：内角与 180° 差 <12° 的顶点直接合并，重算面积/质心/边表并原地写回 `pieces.json`。同一张照片前后对比：

   | | C 的边数 | 拼合结果 | 对接边长差 | 凸包空隙 |
   | --- | --- | --- | --- | --- |
   | 修复前 | 4（C1+C2 被切开） | C3↔B1、C4↔A2（错） | 1.11% | **10.92%** |
   | 修复后 | 3（C1=816.7px 合并成一条） | **C1↔B3、C3↔A2** | 1.08% | **0.55%** |

   UI 上会提示「已合并共线顶点（影子/毛刺造成的假角）：C 4→3」。

11. **「1 个凹形 + 3 个三角形」这条先验应该显式用上** —— 之前的 `notch_ratio_match.py` 只是个独立脚本，`web/pipeline.py` 根本没调用过，等于这条信息白放着。现在 `solve()` 在尺度补偿之后会先判断碎片构成：
    - `notch_applicable()`：恰好 1 块带 **3 个凹顶点**的碎片 + 恰好 3 块无凹顶点碎片 —— 满足才走双射匹配；
    - 调用 `notch_ratio_match.py --match-mode angle`（`--tol-deg 15`），**以「凹形缺口角度 vs 三角形内角」为主判据**穷举 3! 种「三角形→缺口」全排列，**每个三角形只能落一个缺口**；角度打平时用三边比例签名做 tiebreak；
    - `notch_ok()` 做闸门：双射必须成立、平均形状误差 ≤ 0.15、重叠 ≤ 1%；
    - 达标就直接当最终解，**跳过束搜索和 eval_union**；不达标或者碎片构成不符就退回原来的束搜索，行为不变。

    实测 pieces5：墙钟 **19.2s → 3.5s**（省掉 18s 束搜索），重叠 0.00%，缺口 3.40%；拼合关系变成 `A2↔C2 / A6↔B4 / A10↔D1` —— **三个三角形各自只贴住凹形上的一个缺口**，正是这条先验想要的结构（束搜索给出的解里三角形之间还会互相贴）。

    几种 `--match-mode` 的取舍（同一张 pieces5）：

    | 模式 | 判据 | 角度差（三个匹配） | 几何效果 |
    | --- | --- | --- | --- |
    | `angle`（管线默认） | 凹形缺口角 vs 三角内角 | 4.7° / 13.1° / 10.5°，全部 ≤15° | 角度一致性好，但拼缝偏松：hull gap 12.66%、重叠 0.23% |
    | `shape` | 三边归一化比例签名 | 未直接约束 | 拼缝更紧：hull gap 7.15%、重叠 0.0% |
    | `corner` | 凹顶点两邻边比 + 张角 | 同上 | 不如前两者 |

    想让"角度一致"优先就保持 `angle`；想拼得更严丝合缝就把管线里的 `--match-mode` 换成 `shape`。

    注意：双射解用的 `placed_polygon` 是**整块碎片的摆放后多边形**（不是还原出的那 3 个真角），否则顶点数对不上，`render_assembled` 的顶点对拟合会失败。

    **摆放只允许平移 + 旋转，不做等比缩放**（`rigid_fit()`）：`w` 的模长强制为 1，在「角 + 两条邻边」三个点上做最小二乘刚体拟合，把误差平摊到两条壁而不是全扔给一条。所以 `notch_ratio_match.json` 里 `scale` 恒为 `1.000`。

    代价：没法用缩放去"吸收"边长方差。实测两例的对接边长度差：

    | 样例 | 对接 | 两条壁的长度差 | 结果 |
    | --- | --- | --- | --- |
    | pieces5 | T4→缺口2 | **+1.9% / −0.6%** | 几乎严丝合缝 |
    | pieces5 | T3→缺口0 | +3.2% / −5.9% | 贴合 |
    | pieces5 | T2→缺口1 | +13.3% / **+50.3%** | 三角比缺口大，只能压进去 → 重叠 2.67% |
    | 三角形测试图 | T3→缺口0 | −13.1% / −14.7% | 三角偏小 → 留缝 |

    也就是说：**「不留空隙」现在取决于边长方差，而不是摆放自由度**。pieces5 从「缩放版 重叠0.00%/缺口3.26%」变成「刚体版 重叠2.67%/缺口4.29%」。要真正无空隙，得先把小碎片的边长量准（小碎片面积偏差 −10%~−16%，`max_area_triangle` 取内接三角形还偏小），或者允许一个很小的有界缩放。


## 耗时

时长现在**由搜索自动化决定**，不需要调参数：

| 样例 | 自动预算 | 实际总耗时 |
| --- | --- | --- |
| 3 块（一份实测） | 8s | **8.6s**（分割 2.4 + 尺度 1.1 + 搜索 2.4 + 评估 1.2 + 渲染 <1） |
| 4 块（pieces4） | 18s | **27.2s**（搜索 16s） |

拼得不够好会自动加时重搜，最坏情况约 150 秒（硬上限）。碎片越多耗时越长，但**不需要人来选参数**。
